## Architecture

### ADR-001 — Confirm ParaBank as target app
**Decision** — ParaBank (https://parabank.parasoft.com/parabank) is the target application for the discovery run and all evidence in `/evidence/`.

**Context** — The feasibility probe (see progress.md — ParaBank feasibility probe) verified: (a) a real multi-step flow exists (register → overview → open account → detail → transfer → result); (b) clean expected-business-outcome branches exist ("Could not find account #999999999" for account lookup; "Loan Denied" for the Request Loan flow); (c) all interactive elements are native semantic tags (`<a href>`, `<input type=submit/button/text>`, `<select>`), so ARIA roles are trustworthy; (d) no iframes or framesets.

**Alternatives**
- the-internet.herokuapp.com — fragmented single-purpose pages, no coherent multi-step business flow. Kept only as an optional backup if we later want an iframe-specific demo case.
- SauceDemo — DOM too clean (every element has data-test attributes); does not exercise the "legacy / no clean DOM" reality the assignment emphasizes.
- Self-built hostile mock app — high effort, low payoff given ParaBank already hits the pain points.

**Consequences**
- Checkpoints must be DOM-based, not URL-based: probe found that transfer / open-account / loan success is an in-page DOM change at the same URL.
- Locators must handle per-session dynamic names: probe found account links have role=link correctly, but their accessible name is the per-session account number (e.g. "17118") — name alone is not a stable locator, motivating parameterized locators (see ADR-002).
- Safety layer must validate inputs before dispatch: probe found ParaBank's transfer endpoint accepts negative and over-balance amounts (returns "Transfer Complete!" for a -$50 transfer). We cannot rely on the target app to enforce business rules server-side.
- Session-timeout scenario was not exercised in the probe (time cost too high); it is deferred to design-only discussion in REPORT §5.

### ADR-008 — Single-process monolith, functional module boundaries, CLI-driven
**Decision** — One Python process, no runtime service boundaries. CLI-first with two subcommands: `discover` (goal + target → LLM agent loop → writes artifact + evidence) and `replay` (artifact + parameters → deterministic replay → writes evidence + typed result). Modules by function: `models/` (Pydantic artifact types), `executor/` (Playwright backend + `find_matching` + all action executors, per ADR-006/ADR-002), `agent/` (discovery loop: LLM observation/caching per ADR-004, failure-injection orchestration per ADR-005, auto-replay validation gate + reverse-parameterization + fresh-value generation for `generate`-flagged params + fixture pre-replay orchestration per ADR-006), `replay/` (deterministic engine + three-way checkpoint resolver per ADR-005), `escalation/` (injected-overlay takeover per ADR-007), `safety/` (allowlist + input validation + PII redaction), `evidence/` (always-on failure-screenshot capture + structured logs per ADR-004), `storage/` (YAML artifact I/O), `cli.py`. Playwright launched `headless: false` (per ADR-007); no config flag exposes headless. Filesystem-only storage; no DB.

**Context** — §4 ("single process vs services… simpler is fine if justified"), §7 (no queues/clusters/multi-tenant plumbing), §6 (demo = exact commands to run the agent then replay). Modules communicate at method-call granularity over shared typed models; HTTP boundaries would add serialization + a second process for zero evaluation gain. Type-language split: Pydantic models are the container language for the artifact structure itself; JSON Schema is the value-type language for parameter/capture type declarations (per ADR-006).

**Alternatives** — FastAPI frontend/backend split — rejected (cross-process serialization + complex demo path, §7 anti-infra). Microservices per module — rejected, same reason at higher cost. Long-running HTTP server from day one — rejected now; additive later if the §8 "Agent-facing capability interface" stretch goal is taken up (a thin `api/` wraps `replay/`+`storage/`, no existing signatures change — this is how §3.7 "don't paint into a corner" reads in practice). Jupyter-notebook demo — rejected; §6 needs exact reproducible commands.

**Consequences** — Demo path = two shell commands, no service to start (§6). Executor is a class, not a service; a future desktop backend (xa11y) is another class implementing the same interface (ADR-002 seam). Playwright's browser is the only external process launched. Complemented by a future `## Safety` ADR (ADR-safety-pii): PII/credential handling during takeover, allowlist enforcement, pre-dispatch input validation, and the safety envelope around failure-injection when it extends beyond read-only capabilities. REPORT §1/§7 cite this ADR for why we did not build a DB, queue, service mesh, auth layer, plugin system, or browser-based operator console.

**Revision — evaluator-friendly launcher + bundled artifacts (demo-path convenience, no new architecture).** `scripts/run_capability.py` is a thin wrapper over the same `discover`/`replay` cores as `python -m src.cli` (the cores were extracted into `cli.replay_capability` / `cli.discover_capability`, which both the subcommands and the launcher call — the launcher reimplements no wiring). Two modes: **replay** a pre-discovered bundled artifact from `artifacts/` (no API key — reads caller params from the artifact's `metadata.sample_invocation` `$env:` refs) and **discover-then-replay** from a `--goal` (needs `ANTHROPIC_API_KEY`, fail-fast). The launcher's default replay is **non-interactive** (`interactive=False`) so an unattended evaluator never blocks on the 5-min reactive-escalation panel (the `python -m src.cli` power-user path stays `interactive=True`). **Auto-reseed:** ParaBank purges sandbox accounts every ~30-60 min; when a replay returns `hard_failure(technical_error)` whose message contains a login/stale-credential keyword (incl. ParaBank's observed "internal error" / "could not be verified" / "could not find account" texts), the launcher re-runs the seed script, rewrites the `PARABANK_*` lines in `.env` in place (preserving the API key + other lines), and retries the replay ONCE — never on other outcomes. Bundled artifacts stay §3.4/§9-safe ({{template}} params + `$env:` sources, no literal secrets). This is additive, no existing signatures changed. REPORT §6 references the launcher as the friendly entry point atop the canonical two-command demo.

### ADR-009 — Registry-based validation supersedes fixture composition
**Decision** — The auto-replay validation gate validates a capability by replaying it with `caller_parameters` that reference **pre-existing test data** (a small registry of accounts we seeded on the target, held in a gitignored `.env`), NOT by composing a fresh-session fixture per invocation. Discovery is invoked with those same `caller_parameters`; emission (a) reverse-parameterizes their literal values out of every step field into `{{name}}` templates and declares each in `parameters`, and (b) records the exact values used in `artifact.metadata.sample_invocation`. The validation gate reads `sample_invocation` back and passes it to `ReplayEngine.replay`; if a capability declares `parameters` but has no `sample_invocation`, the gate cannot execute and marks `validated: false` with a clear reason.

**Context** — A design review established that per-invocation fixture composition (the ADR-006 β approach) does not match the assignment's target environment: §2's canonical goal is "look up **member 12345**" — the caller supplies an **existing** id (§3.2 "typed input parameters … e.g. a member ID"). A real bank AI agent operates on existing customer accounts, not freshly-registered ones, so "register a new user every replay" inverts the production semantic and is the more expensive path (§1 "cheaply"). A pre-seeded **test-data registry** is standard Test Data Management practice in the Playwright/Selenium ecosystems and is specifically recommended for banking/finance QA (sources cited in the v3 review). It also yields the stronger multi-tenant reuse story (§3.7): one tenant-agnostic parameterized artifact + a per-tenant `.env` registry, rather than re-recording per tenant.

**Alternatives** — Per-invocation fixture composition (rejected: mismatches §1 "cheaply" and real banking semantics — you do not create a member to read a member). Registry+fixture hybrid (rejected as an unprincipled default per v3 §6; fixture composition remains available but is not the gate mechanism). Structural/element-existence checkpoints in place of parameterized data (rejected earlier, v3 alternative 3).

**Consequences** —
- Fixture-**as-capability** remains valid: a fixture is still a discoverable capability whose schema shape (a `generate: unique_string` username, `parameters`, `captures`, `export`) is unchanged. It is simply no longer the validation mechanism.
- `artifact.metadata.sample_invocation: dict[str,str] | None` is added; it is required-if-`parameters`-exist (a parameterized capability with no `sample_invocation` cannot be auto-validated) and `None` for self-contained capabilities (e.g. a fixture that only uses `generate`).
- Registry infrastructure is added: `.env.example` (committed, placeholders), `.env` (gitignored, §9), and `scripts/seed_parabank_accounts.py` (a one-shot Playwright provisioning script, no LLM).
- REPORT §4 multi-tenant story shifts to "per-tenant `.env` registries reuse the same artifact across tenants."
- The `metadata.validation_fixture` and `metadata.input_mapping` fields (proposed under ADR-006 β, never used in a shipped artifact) are removed from the schema; the `ReplayEngine` fixture-composition branch and `src/replay/fixture_composer.py` become dead code and are removed.
- **Deferred (future `## Safety` ADR):** `.env` credential handling, per-tenant registry isolation, CI fallback when the registry is absent, and preventing registry values from leaking into artifacts/logs (redaction). The current design keeps `.env` gitignored (§9) and never writes registry values into artifacts; log/evidence redaction of typed credential values is a known open item flagged for that ADR.

## Artifact schema

### ADR-002 — Platform-agnostic semantic locators with fallback chain and parameter interpolation
**Decision** — Locators in the artifact are stored as platform-agnostic semantic descriptors (role + name + optional href/id/structural anchor + an ordered fallback chain), NOT as raw Playwright API calls. A dedicated Executor layer translates these descriptors into Playwright calls at replay time. Locator fields support parameter interpolation (e.g. `href_pattern: "activity.htm?id={account_id}"`, or `name: "{button_transfer_label}"` for cross-tenant UI-copy variance).

**Context** — Probe showed ARIA roles are trustworthy on ParaBank (all-native tags), but accessible names are per-session dynamic for account links, and id/data-testid coverage is inconsistent (form fields have ids: `#amount`, `#fromAccountId`, `#balance`; buttons and account/nav links do not). A single locator strategy is insufficient, and ordering (fallback) matters. This decoupling is intentionally designed to make the REPORT §4 write-up story credible without actually implementing multi-surface support — the assignment (§3.7, §7) explicitly says core abstractions must not paint us into a corner, but explicitly does NOT reward building scaling infrastructure prematurely. The Executor layer stays single-backend (Playwright) in this deliverable; alternative backends (xa11y for desktop, etc.) are discussed in REPORT §4 only, not built. Parameter interpolation serves two distinct purposes simultaneously: (1) runtime business data (e.g. `account_id` supplied per invocation), and (2) cross-tenant environment/UI variance (e.g. `tenant_base_url`, `button_transfer_label`). This links §2 (schema) to §4 (multi-tenant) with a single mechanism.

**Alternatives**
- Raw Playwright selectors in the artifact — fastest to build, but encodes tool-specific syntax into what's meant to be a portable capability and forecloses the §4 heterogeneity/multi-tenant story.
- Accessibility-tree-only (role + name) — fails on the observed "role trustworthy but name per-session dynamic" case (account links).
- Related open question (deferred): whether to add a screenshot+coordinate strategy as the final fallback in the chain, for surfaces where even ARIA is unusable. Deferred until we see whether the discovery run against ParaBank actually exercises a case where ARIA-based locators fail. If added later, it will be recorded as ADR-002a or a v2 revision.

**Consequences**
- Schema needs a locator type with fields: `strategy` (e.g. role_name, href_pattern, css_id, text), an ordered `fallbacks` list, and parameter interpolation via `{param_name}` placeholders resolved from the artifact's declared parameters block.
- Executor layer becomes the seam for future backends (documented in REPORT §4; not implemented).
- Artifact's parameters block doubles as the typed capability contract that any calling agent reads to know what inputs are required (directly supports Requirement 3.2's "typed input parameters" and lays groundwork for the optional stretch goal "Agent-facing capability interface" if we later pick it up).

### ADR-006 — `captures` (export flag replacing outputs), fresh-value synthesis, `find_matching`, and the auto-replay validation gate
**Superseded in part by ADR-9 (validation semantics).** Fixture-as-capability (this ADR's β approach) remains the schema shape for artifacts that self-generate data via `generate` markers. The `validation_fixture` and `input_mapping` metadata fields originally proposed here are **no longer part of the schema** — the validation gate uses `metadata.sample_invocation` per ADR-9. The rest of this ADR (parameters/captures/exports/`{{name}}` interpolation, `find_matching`, `generate` marker, untraceable-field handling) remains authoritative.

**Decision** — Two typed (JSON-Schema) data-flow categories: `parameters` (caller-provided at replay start) and `captures` (runtime-discovered; each bound by a step via `capture: {variable, source}`; consumed anywhere via `{{name}}` interpolation — values, url templates, locator fields, checkpoint `required_phrases`). No separate `outputs` category: a capture with `export: true` (or `returned_as: <alias>`) joins the caller-facing return contract. Additions:
- `find_matching` action (agent tool set = click, type_text, navigate, read_text, find_matching, finish): `candidates: <captured_list_var>`, `probe: {action, locator, checkpoint}`, `capture: {variable, value_from: "candidate", export?, returned_as?}`. Replay iterates candidates and captures the first whose probe checkpoint passes — pure iteration + `text_all_present`, no LLM.
- `capture.source` supports `extract: {pattern, from}` (e.g. `pattern: "id=(\\d+)", from: "href"`) for compound-value extraction.
- Array types (`string[]`) MUST be supported for captures — hard prerequisite for `find_matching.candidates`.
- `generate` marker on a parameter (`generate: unique_string | unique_email | timestamp`): the harness synthesizes a fresh value per invocation instead of consuming a caller value. Only `unique_string` needed now (usernames; fixture_discovery Q9 confirmed a replayed literal username hits ParaBank's duplicate rejection).
- β fixture-as-capability: a capability may declare metadata `validation_fixture: <capability_name>` + `input_mapping: {<target_param>: <fixture_capture>}`. The validation gate replays the fixture first, maps its exported captures into the target's parameters, then replays the target. Two-level depth; no recursion/cycle detection in this deliverable.
- Auto-replay self-validation gate: after discovery the system replays the artifact (fixture pre-run if declared) against a fresh session; pass → `validated: true`, enters the artifact store; fail → `validated: false`, excluded from delivery, failure log kept (optional discovery retry with prompt steering). The validation replay doubles as §6's "replay run with logs" evidence.

**Context** — Run 2 (steps 6–8 → 14): one discovered value fanned into a locator, a URL template, a checkpoint phrase, and a returned output → one unified `{{name}}` mechanism over parameters ∪ captures. Prior-art (research_adr6_adr7): Skyvern/Argo/CrewAI keep parameters vs per-step outputs but have no separate "final output" — so export-flag, not a third category. `find_matching` resolves the review Blocker (Run 2 step 7 hardcoded `activity.htm?id=14010`, non-replay-safe); the fixture_discovery run confirmed the LLM-manual-iteration alternative risks silent dead artifacts, which the validation gate catches. β + `generate` validated end-to-end by the fixture_discovery run (register+open-savings discoverable in 21 steps, artifact replay-safe — Q7/Q9/Q11).

**Alternatives** — Three parallel categories (parameters/captures/outputs) — rejected; captures and outputs are mechanically identical (visibility bit only). Untyped variable bag (Postman/RF) — rejected (§3.2 typed contract). Single-blob shared state (LangGraph) — rejected (under-specifies read/write, needs reducers). Pure `{variable, source}` without a search primitive — rejected (Run 2's savings_id needs enumerate-and-match; replay has no LLM). γ per-target hand-written Python fixture — rejected (adr_gap4_consultation memo): introduces a human-authored setup as a second entity class alongside artifacts, violating §1's "model discovers"; β at ~100 lines of orchestration on the existing replay engine is affordable and keeps one entity type.

**Consequences** — Schema: `parameters` block (JSON Schema object, optional `generate`), `captures` block (`{name, type, source_step, export?, returned_as?}`), `find_matching` step type, `validation_fixture`/`input_mapping` metadata, `validated` flag. Gap #4b (emission-stage rule): a finish field that cannot be traced to a single source step cannot be `export: true` — it is dropped from outputs with a warning entry at emission (not deferred to the validation gate, which only checks the checkpoint). Interpolation on undefined names fails loudly. Exported captures = typed function-return contract; parameters (incl. generate-flagged) = typed function-signature contract — directly supports the future "Agent-facing capability interface" stretch goal with no schema addition. Fixtures are discovered like any capability; the production method is swappable (LLM discovery normally, hand-authored artifact if finicky) — the replay engine and data model treat them identically.

## Determinism & error handling

### ADR-004 — Prompt caching + ARIA-only observation by default, screenshot as fallback; evidence screenshots always-on
**Decision** — **Scope: this ADR governs screenshots included in the LLM's observation input only; evidence-layer screenshot capture is a separate, always-on concern (see Consequences).** Enable Anthropic prompt caching (`cache_control: {"type":"ephemeral"}` on system prompt + tools + a rolling breakpoint on the last message) — turns the raw-quadratic history resend into approximately linear billed cost. Default observation: ARIA text snapshot only (`locator.aria_snapshot()`), sent every step. Screenshot fallback (opt-in per step; attached only to the current turn — it never enters the cached prefix, so a fallback event does not invalidate prior cache) fires on defined triggers: (a) the previous step's locator resolution returned 0 matches; (b) the LLM calls a `request_screenshot` tool. Each new trigger requires an ADR revision.

**Context** — Run 1: 8 steps / 124k input / ~$0.38, per-step input grew 4.6k→25.9k (quadratic). Run 2 (caching on): 14 steps / 337k raw / 81k billed / ~$0.24, cache-hit 1.000, ~76% saved (reconfirmed by fixture_discovery: 21 steps, ~$0.48, per-step billed flat). Run 1 Q7: no reasoning step referenced screenshot-only information; every decision traced to ARIA text — carried with the findings' own hedges: only one run, on ParaBank's all-native-semantic surface (the favorable case), so sustained validation on more surfaces would be needed to strengthen this default. Image tokens ≈ ~40% (Run 1) / ~42% (Run 2, by calculation) of raw input.

**Alternatives** — ARIA + screenshot every step (Run 2 pattern) — safest but pays image cost unconditionally; post-caching it is affordable, so the ARIA-default rests on Q7 sufficiency more than on cost. Screenshot-only, no ARIA — wastes ParaBank's high-quality ARIA tree. Screenshot only on hard failure, not on 0-match retry — too conservative: 0-match is a plausible signal that ARIA alone is insufficient, and a screenshot offers a second perception channel to disambiguate (softened from an earlier over-claim — Run 1 Q7 shows the login 0-match was actually resolved via positional `nth`, not the screenshot).

**Consequences** — Executor exposes a `request_screenshot` tool and tracks per-turn locator-resolution outcomes to auto-inject a screenshot on the turn after a 0-match. **Evidence-layer capture (always-on, distinct concern):** the executor MUST capture a plain `page.screenshot()` to evidence storage on every checkpoint `hard_failure` and every escalation event, regardless of the LLM-observation policy and distinct from the LLM-facing `request_screenshot` tool (satisfies §3.5 "richer signal on failure" and ADR-005's `hard_failure` payload; owned by `evidence/` per ADR-008). Revisit trigger: sustained ARIA insufficiency on a new surface (legacy `<div onclick>` web, desktop backend) flips the default or expands the trigger set.

### ADR-005 — Checkpoint = `text_all_present` with interpolation, async polling, three-way outcomes; auto-authored `expected_outcomes`
**Decision** — Checkpoint matching = `text_all_present`: an ordered `required_phrases` list must all appear (AND) as substrings of a `target` DOM region's text; phrases support `{{name}}` interpolation over parameters ∪ captures. Async-tolerant polling (`wait_ms` default 5000 — a heuristic default, not empirically calibrated; Run 2 rendered in ~1s — `poll_interval_ms` default 500). Three-way outcome: `success` → bind exported captures; else any `expected_outcomes[i]` (each a named `{name, required_phrases}`) matches → `{status: business_outcome, name, phrases}` (no capture binding); else polling exhausts `wait_ms` → `checkpoint_timeout` → escalate per ADR-007 → if the human Aborts or escalation is unavailable → `{status: hard_failure, step_id, expected, observed: last ARIA + evidence screenshot}`. (Recoverable conditions = a separate step-level `pre_action_handlers` mechanism, deferred.)

Auto-authoring, no human step: success `required_phrases` come from extending `finish` with a required `success_observed_phrases: string[]` — the LLM lists the ARIA strings it cited as success evidence; the system reverse-parameterizes matches against parameters ∪ captures and (Gap #1) reverse-looks-up each phrase to its earliest observation step, attaching the checkpoint there and emitting per-step checkpoints when phrases split across pages (confirmed necessary in Run 2 transfer→balance AND fixture_discovery registration→overview). Reverse-parameterization guardrails (Gap #2): longest-value-first, token-boundary matching, skip values <3 chars. `expected_outcomes` are authored by a failure-injection sub-run scoped to `read` capabilities only; each injection is recorded only if all three hold: HTTP 200, the observed page mentions the injected value, and no error-redirect. `capability_type` (read|write|mutating) inference is **pattern-based, not URL-based**: the auth prologue is the sub-sequence `type_text(username) + type_text(password) + click(Log In/Login/Sign In)`, everything up to its last action is prologue and excluded; flows without this pattern (e.g. the register-then-auto-login fixture) have no prologue and all actions count. Async-tolerant checkpoint targeting: when the discovery LLM works around a transient AJAX result panel by verifying on a stable secondary surface (Run 2 step 12; fixture_discovery step 20), the extracted checkpoint SHOULD target the stable surface — the LLM's discovered workaround IS the replay-robust checkpoint location.

**Context** — ADR-001: ParaBank success = same-URL DOM change → URL matching rejected; §3.3 requires distinguishing expected business outcomes / recoverable conditions / hard failures. Run 2 step 11→13: success recognized via ARIA text ("Transfer Complete!" + amount + both account ids), three of which are parameter/capture-bound → element-existence matching fails on per-session dynamic names (Run 1 account links). Run 2 step 12 async false-negative → a single snapshot would wrongly hard_fail. Failure-injection is scoped to `read` because the probe found ParaBank's transfer endpoint accepts negative/over-balance amounts → injecting into write/mutating capabilities would perform real destructive writes; write/mutating capabilities therefore have empty `expected_outcomes` this deliverable. Gap #0 pattern-vs-URL was disambiguated by the fixture_discovery run: a URL-based detector would strip the whole registration and misclassify the fixture as `read` → destructive injection. RPA analogy: deterministic replay precludes runtime LLM judgment (Skyvern `terminated`, browser-use judge), placing us in RPA's Business-vs-System-Exception space — except the decisions are authored automatically by the discovery LLM, not by a human developer.

**Alternatives** — URL matching (rejected, ADR-001). Element-existence role+name (rejected; per-session dynamic names). Single-snapshot check (rejected; Run 2 step 12). Success-only with no business branch (rejected; collapses §3.3's business outcomes into hard failures). Human-authored `expected_outcomes` (rejected; §1 "model discovers" — auto-authored via the failure-injection sub-run instead).

**Consequences** — Schema: `checkpoint = {success: {required_phrases, target}, expected_outcomes: [{name, required_phrases}], target (default #rightPanel — a ParaBank config default, overridable), wait_ms, poll_interval_ms}`. Replay engine implements the three-way polling resolver; `checkpoint_timeout` integrates with ADR-007 escalation. Pipeline stance: the artifact is directly replay-ready after discovery — no human review step; humans enter only at runtime escalation (ADR-007); post-hoc YAML edits are possible but not a workflow correctness depends on. REPORT §3 documents: write/mutating capabilities have empty `expected_outcomes` (ParaBank's accept-anything transfer as the example); the 3-condition injection criterion is conservative and may discard legitimate outcomes that don't echo the injected value (e.g. loan denial — a write outcome we don't inject anyway); and short/format-variant values (typed `25` vs displayed `$25.00`) may not reverse-parameterize and may hardcode.

**Forward reference (future Safety ADR)** — registry-based validation (per ADR-9) introduces new safety surfaces not addressed here: `.env` credential handling and rotation, per-tenant registry isolation, fallback behavior when the registry is absent in CI environments, and prevention of registry-value leakage into artifacts or logs. A future ADR under `## Safety` will address these; the current design keeps `.env` gitignored per §9 and never writes registry values into artifacts (evidence/log redaction of typed credential values remains a known open item for that ADR).

**Phase-3 revision — `hard_failure` is reserved for four named subtypes (D5/D6).** The original ADR-005 collapsed every non-success/non-business_outcome into a bare `hard_failure`. Phase-3 splits the outcome by *who could resolve it*, carried in `ReplayResult.reason`: (1) `stub_unavailable` — a stuck condition (checkpoint_timeout / locator_exhausted / safety_violation / find_matching_exhausted) arose but no human was reachable (the `StubEscalationHandler` / any handler with `is_interactive=False`, e.g. unattended CI); (2) `human_aborted` — a human WAS escalated to and chose Abort (carries their `operator_note`); (3) `escalation_exhausted[:detail]` — the system escalated to a human and STILL could not resolve the stuck condition: the bounded escalate↔retry loop ran out of rounds (`checkpoint_unresolved_after_escalation` / `action_unresolved_after_escalation`), or the human's response / take-over-Done window timed out (`no_response_or_takeover_timeout`). This is a *semantic* exhaustion — the human did not choose Abort and nothing crashed; (4) `technical_error:<detail>` — a failure no human can fix (Playwright crash, network, an unhandled exception, capture-binding failure, `human_input` timeout). **Replay-layer upgrade:** the four stuck conditions above no longer go straight to `hard_failure` — they route through ADR-007 escalation first when `is_interactive`, and only settle to `human_aborted` (Abort), `escalation_exhausted` (loop/response exhausted), or `stub_unavailable` (no human). **Take-over is a two-phase hand-off (Bug-fix):** clicking "Take over & resume" does NOT immediately re-observe — the panel switches to PLANNED mode (prompt + single Done) so the human actually acts in the browser; only on Done does the engine re-observe the DOM and re-evaluate the checkpoint once (pass → continue; still stuck → escalate again, bounded). The hand-off **survives navigation** (Phase-B fix): because acting often means navigating, and `add_init_script` re-injects the panel on each new document in its DEFAULT (reactive) mode, the handler re-applies PLANNED mode on every page `load` during the wait — so the Done button never disappears mid-take-over and the human is never stranded (which would otherwise force a 5-min timeout → `escalation_exhausted`). **Executor-layer stays technical:** the executor never escalates on its own — a raw technical exception it raises propagates directly to `technical_error:<detail>` (a human at a takeover panel cannot repair a crashed browser). The escalate↔retry loop is bounded (`_MAX_ESCALATION_ROUNDS = 3`); exhausting it is `escalation_exhausted`, NOT `technical_error` (the earlier build mislabeled it). CLI decodes all four subtypes for the operator.

**Business-outcome vs capture ordering (bug fix).** A step may carry BOTH a success capture and a checkpoint whose `expected_outcomes` declare recognized business outcomes (schema-draft §10: "no such account is a legitimate answer, not a crash"). The replay engine executes the action, then **binds the success captures, then evaluates the checkpoint** — this order is REQUIRED because a step's success phrases may reference that same step's captures (e.g. `{{account_type}}`/`{{balance}}`), so `interpolate` would raise on the unbound name if the checkpoint were evaluated first. A capture can, however, fail precisely BECAUSE the page reached a business outcome (the success pattern like `CHECKING` is absent on a "Could not find account #..." page). The rule: **on a `CaptureBindingError`, evaluate the step's `expected_outcomes` FIRST (capture-independent, via `resolve_checkpoint(business_only=True)`, which skips success-phrase interpolation) — a match returns `business_outcome(name)`; only a capture failure with NO matching business outcome is `technical_error`.** This is *not* an exception-recovery patch of wrong semantics: because success phrases legitimately depend on same-step captures, capture necessarily precedes success evaluation, so business-outcome recognition is correctly the capture-failure classifier. Success still wins when both could match: on a successful capture the normal `resolve_checkpoint` evaluates success phrases BEFORE expected_outcomes, so a business outcome never pre-empts a genuine success. (Previously a capture failure short-circuited to `technical_error`, so `expected_outcomes` — including the ones authored by the failure-injection sub-run — were never consulted at replay; this fix makes those authored phrases actually used.)

## Escalation & handoff

### ADR-007 — Human takeover via injected in-browser panel + `expose_binding` → asyncio event; always-headed
**Decision** — Playwright is launched `headless: false` by default; headless mode is out of scope for this deliverable. Takeover UI = an in-browser overlay injected into the live page (`page.add_init_script`, survives navigation) as a fixed, non-modal, right-side collapsible panel above page content, showing capability name, current step id, why we stopped, and three actions — Resume / Take over then resume / Abort; the collapsed state keeps an unmistakable "paused" indicator. Resume signal: buttons call `window.resumeAutomation(outcome)`, a `page.expose_binding()` bound to a Python callback that sets an `asyncio.Event` (or resolves a Future) the paused replay coroutine awaits. After Resume or Take-over-then-resume the engine re-reads the DOM before executing the next step. During takeover, observation recording is suspended (no screenshots/DOM/ARIA to evidence — only boundary events + a redacted `dom_diff_summary`), so credentials/PII a human enters never reach evidence. Escalation triggers: `checkpoint_timeout` (per ADR-005), locator resolution failing after N attempts, safety guardrail hit (future), explicit LLM signal during discovery (future stretch).

**Two modes (Phase-2 addition) — reactive escalation + planned intervention.** The same overlay serves both.
*Reactive* (above) fires when the system detects it is **stuck** (checkpoint timeout / locator fail / safety) and shows **three** buttons (Resume / Take over & resume / Abort). *Planned intervention* fires **by design**: at discovery the LLM may call a `request_human_input(prompt, reason)` tool for a step that genuinely cannot be automated (2FA code, captcha, a person-only choice, §3.6 "a risky/irreversible step needs a person"). Emission records it as a `human_input` step (`{prompt, reason, timeout_ms}`, prompt shown VERBATIM, never reverse-parameterized), so **every replay pauses there**; the executor invokes `escalation_handler.escalate_planned`, and the panel enters **planned mode** — the prompt + reason + a **single "Done"** button. Semantics as **explicit human consent**: the human performs the action directly on the page and clicks Done; **no value is returned to the system** (the human acts on the page, the LLM/replay simply re-observes the DOM and continues). `is_takeover_active` suspends observation during the planned re-read exactly as for reactive takeover. `timeout_ms` (default 60000) hard-caps the wait — a planned timeout becomes a replay `hard_failure` (distinct from reactive, which blocks with no timeout this deliverable). Consequences: (a) `capability_type` for any capability containing a `human_input` step is classified **`mutating`** (conservative — a human is changing state); (b) the auto-replay validation gate **cannot** auto-validate such a capability (no human is present, gate is unattended/headless) — it **detects the `human_input` step and skips**, leaving `validated: false` with `metadata.validation_skip_reason = "requires_human_input"` (a non-failure skip, not a `hard_failure`); (c) `human_outcome` in the §9 evidence event gains `planned_done`. Boundary: the executor calls `escalate_planned` on an **injected** (duck-typed) handler — it never imports `src/escalation` (ADR-008); the `ReplayEngine` wires the handler onto the executor at replay start, and the CLI injects the real `PlaywrightEscalationHandler` (via a `page_provider` lazy accessor) into discovery, the validation gate, and replay.

**Context** — §3.6: pause on stuck → human takes control of the same live session → hand back → record what the human did; the scope note puts a full co-browsing operator console out of scope but requires the mechanism itself to be real. Q2 research: cloud agents (OpenAI Operator, Browserbase, Cloudflare Browser Run, Nova Act) use CDP-screencast live views because their browser runs remotely; on a local machine with a display the OS window IS the live view — no streaming infrastructure needed, so an injected overlay is the correctly-sized tool for local deployment. Run 2 step 12 (and fixture_discovery step 20) async false-negative is exactly this case: checkpoint timeout → human glances at the real page → Resume → re-observe. Two safety borrowings from Operator: suspend observation during takeover; resume by re-reading the DOM.

**Alternatives** — CLI `input()` (rejected; primitive, no context surfaced, no button distinction). Separate web operator console (rejected; §3.6 scope note). Native OS dialog tkinter/pyautogui (rejected; blocks the asyncio loop, steals focus). Local FastAPI at localhost (rejected now; highest moving parts; reasonable only for a future remote/multi-operator console — REPORT §5). Playwright `page.pause()` as sole mechanism (rejected; fixed Inspector UI, non-customizable resume, no Takeover-vs-Resume distinction, requires headed anyway).

**Consequences** — Per-trigger Resume semantics: **checkpoint timeout** → Resume = re-poll the same checkpoint (fresh `wait_ms`); Take-over-then-resume = re-observe DOM, evaluate checkpoint once, if pass continue. **locator fail after N** → Resume = retry the current step's action; Take-over-then-resume = re-observe DOM, continue from next step. **safety guardrail** → deferred to a future safety ADR (likely not permitted). **explicit LLM signal (discovery)** → out of scope (future stretch). Takeover evidence event: `{escalation_at_step, reason, timestamp, human_outcome: resume|takeover_resume|abort, duration_s, dom_diff_summary, operator_note}` — `operator_note` is an optional free-text "what did you do?" the operator fills on resume (a cheap human-authored action summary complementing the coarse DOM diff, better satisfying §3.6 than the diff alone). Sensitive parameter values are redacted before surfacing to the panel. Limitations (REPORT §5): always-headed + human escalation ⇒ no unattended batch replay in this deliverable — true unattended operation would need capabilities designed to never escalate or a queued-escalation mechanism; both future work, not built.

**Phase-3 revision — discovery-time triggers are now live, and reactive escalations are transformed into planned `human_input` steps (D2/D3).** The original ADR-007 left three escalation triggers as "future": **safety guardrail**, **locator fail after N during discovery**, and **explicit stuck signal during discovery**. Phase-3 activates the reactive triggers *during the discovery loop* (not only during replay), gated on `escalation_handler.is_interactive` so the default stub keeps the Phase-1/2 termination (`max_steps` / `stuck`) and all existing loop tests are unchanged. Live discovery triggers: (1) **consecutive locator fails = 3** (D2 threshold; the counter resets on ANY successful action — a success is progress); (2) **safety violation** (a `SafetyViolationError` surfaced by the executor — the safety module itself is still future, but the trigger + routing exist); (3) **max steps without finish** — Resume grants a bounded extra step budget (+5), Abort ends discovery with status `aborted`. **Reactive→planned transformation (D3):** every discovery-time escalation the operator *resumes or takes over* is recorded as a `human_input` step in the emitted artifact (`prompt` synthesized from the escalation context, `reason` = the escalation reason). This is the key determinism guarantee — a flow that needed a human once during discovery re-triggers the SAME human intervention point on every replay, rather than silently diverging. It also composes with the Phase-2 rule: because the artifact now contains a `human_input` step, the auto-replay validation gate detects it and skips (`validation_skip_reason = "requires_human_input"`), so an escalation-shaped capability is never falsely auto-validated. Determinism is preserved: discovery still emits a fully typed artifact; the only "LLM-free replay" caveat is the intended human pause, which was always part of the recorded flow.

**Revision — escalation hints (added post-hoc) + smart dialog dismiss (D1-α / D2-β / D3-α; Gap 2 Level A refined).**
*Escalation hints:* steps with escalation-triggerable actions (`navigate`, `find_matching`, checkpoint-bearing, `human_input`) carry a `metadata.escalation_hint` field populated at emission time via a SECONDARY LLM call (`src/agent/hints.py::generate_step_hints`). The discovery main loop's system prompt and tool schema are UNCHANGED and never expose `step_intents`, so the loop remains 100% goal-driven (§3.1) — hints are the model's post-hoc description of an already-discovered capability, authored from a bounded step summary (ids + action + locator/url/prompt gist + checkpoint phrases, NOT the observation history; `max_tokens=600`, ~$0.05). Injection sub-runs pass `generate_hints=False` (throwaway artifacts don't pay). Generated hints pass through the ADR-9 caller-parameter reverse-parameterization pipeline (`emission.reverse_parameterize`) BEFORE persistence, so session-specific values become `{{name}}` templates and no tenant data leaks into the artifact (§3.7/§9). Hints render in the escalation panel below "Reason:" as an "About this step:" row (`src/escalation/panel_script.py::setHint`), shown in all three modes (reactive three-button, planned single-Done, take-over→planned) and hidden entirely when absent; old artifacts without the field degrade gracefully (row stays hidden, no crash). Data flow: `ReplayEngine._escalate` reads `step.metadata.escalation_hint` → `EscalationContext.hint` → handler → panel ctx; for `human_input` the executor passes `hint=` into `escalate_planned`. Typed `StepMetadata` (not an untyped dict) keeps the strict schema (schema-draft §5).
*Smart dialog dismiss:* the executor registers a page-level `dialog` handler (`PlaywrightExecutor._handle_dialog`) that dismisses `alert` and `beforeunload` (non-blocking side effects; `beforeunload=dismiss` is the user-locked choice this deliverable, `accept` was the review's alternative); `confirm` and `prompt` intentionally FALL THROUGH unresolved — the page then blocks, the checkpoint times out, and reactive escalation hands the operator explicit control via the panel. Registering any handler disables Playwright's default auto-dismiss, so this is a deliberate choice of which dialog types we own. (Reviewer notes: true HTTP Basic Auth is not delivered via the `dialog` event — `http_credentials` on the context is the real fix — and per-dialog human arbitration is future work; both deferred.)

## Safety

### ADR-010 — Credential parameterization is a hard emission requirement (§3.4/§9)
**Decision** — Login credentials (and other secrets) MUST NOT be persisted as literals in an emitted artifact; they are always `{{name}}` placeholders supplied at replay. Emission enforces this with a **B2+B1 hybrid** plus a new `Parameter.sensitive: true` flag:
- **Detection = field-name matching ONLY (decision Q1).** A conservative case-insensitive pattern set (`password|pwd`, `user(name|id)|login|signin`, `email`, `ssn`, `pin`, `otp`, `token`, `api_key`, `secret`, `credential`) is matched against a locator's `name/label/placeholder/id/text` and against caller-parameter names (`src/agent/credentials.py`). **No positional or value-shape heuristic is ever used to parameterize** — that would misclassify non-credential fields. Deliberate deviation from the brief's list: **"account" is excluded** (it collides with the legitimate `account_id` parameter — the exact false positive Q1 forbids).
- **B2 (primary, auto-parameterize).** After the ADR-9 reverse-parameterization pass, any `type_text` whose value is still a literal AND whose field carries a credential name is rewritten to `{{canonical}}` (e.g. `{{username}}`, `{{password}}`), and the parameter is declared `sensitive: true` (caller-required). Caller parameters whose *name* is a credential are also marked `sensitive: true`.
- **B1 (safety net, refuse-to-emit).** After B2, any remaining `type_text` holding a **credential-SHAPED literal** (value-shape heuristic: len≥6 with letters+digits — used ONLY to refuse, never to parameterize) whose field was NOT credential-named raises `CredentialsHardcodedError` with an actionable, **value-redacted** message (add a credential label, or pass the value as `--caller-params-from-env`). This catches nameless credential fields (e.g. ParaBank's `role_nth` login inputs) that B2's field-name detection cannot see. A false positive here is a loud, safe over-refusal — never a silently mis-named parameter.
- **LLM must not invent credentials (decision Q2).** The discovery system prompt requires the LLM to obtain any credential not present in caller parameters via `request_human_input` (one call per credential), never from the goal text.

**Scope / honesty (unchanged from the design review):** this fixes the **artifact**. The discovery **evidence** (`evidence/step_*_action.json`) and any credentials embedded in the goal→system-prompt are still captured in cleartext — full §3.4 compliance additionally needs evidence/log redaction (the `sensitive` flag is the forward hook the future Safety redactor will honor) and not embedding creds in the goal. Those remain deferred to the future Safety module (REPORT §7 Cuts). Cross-tenant reuse (§3.7) is verified end-to-end: the same artifact replays against a second freshly-seeded ParaBank tenant using only different caller parameters.

### ADR-011 — Source captures poll for async-rendered values (replay robustness)
**Decision** — A source-based capture that carries a regex `extract` now **polls** the target element until the pattern matches or a budget elapses (`_CAPTURE_WAIT_MS = 5000`, `_CAPTURE_POLL_MS = 250`, `src/replay/engine.py::_extract_source`), mirroring the checkpoint wait (ADR-005). Rationale: ParaBank populates account-detail fields (Account Type / Balance) via AJAX **after** navigation, so a single immediate read raced the render and produced a `CaptureBindingError` (the long-flagged capture-async-render gap: checkpoints polled, captures did not). Only the single-value regex-extract path polls; the `extract.all` (list) and no-`extract` (raw-text) paths short-circuit unchanged. A genuine miss still raises the same informative `CaptureBindingError` after the budget (→ `hard_failure(technical_error)`), so real failures are not masked — the only cost is up to `_CAPTURE_WAIT_MS` of waiting when a value truly never renders. This is what flips the credential-parameterized `lookup_checking_balance` capability to `validated: true` and lets the cross-tenant replay complete deterministically. (Surfaced by the ADR-010 cross-tenant verification; recorded as its own decision rather than folded into ADR-010.)

### ADR-012 — Runtime safety module built + wired; mutating-consent gate (D1) + discovery-time enforcement (D3)
**Decision** — The `## Safety` layer forward-referenced by ADR-004/005/007/008/009 is now **built** as
`src/safety/` (duck-typed, imports nothing from other `src/` packages — ADR-008 boundary) and wired into the
production replay path:
- **`SafetyGate`** composes two checkers and exposes two hooks. `check_action(action)` runs in the executor
  **before every Playwright dispatch** (`PlaywrightExecutor.execute_action`): allowlist domain
  (`parabank.parasoft.com` only) + sanctioned action-type set (click / type_text / navigate / read_text /
  find_matching / human_input). `check_capability(artifact)` runs at **replay pre-flight** in `ReplayEngine.replay`:
  allowlist-domain coverage over navigate steps + a `capability_type` sanity check (a declared `read` must not
  contain a post-login `type_text`). A violation raises `SafetyViolationError(rule_name)`, which the engine
  converts to `hard_failure(reason="safety_blocked:<rule>")` — **terminal, not escalated** (a human cannot
  un-break a mis-declared capability). The gate is **enforcing by default** but injected only by the CLI replay
  path (`src/cli.py::replay_capability`); `SafetyGate.permissive()` (enforce=False) is the default elsewhere so
  discovery/unit tests are unaffected. The allowlist is a **hardcoded code constant** (`parabank_allowlist.py`),
  NOT a config file — per §7 anti-scaling (a different target ships its own allowlist module of the same shape).
- **`PIIRedactor`** (declaration-based, ADR-010's `sensitive:true` forward hook) redacts secret VALUES to
  `[REDACTED]` in discovery evidence `.txt`/`.json`: the values of `sensitive:true` params (when an artifact is
  supplied) plus a case-insensitive field-name fallback (`password`/`ssn`/`pin`) and JSON key/value pairs.
  `account_id` is deliberately preserved for debuggability. Screenshots are NOT redacted (deferred, REPORT §7).

**D1 fix — mutating capabilities require explicit consent (2026-08-25).** Ground-truth verification showed
`python scripts/run_capability.py --artifact-name transfer_funds` (no flag) **succeeded and moved real $10**
(exit 0) — there was no gate, only a `[WARN]` print. Fix: `SafetyGate(allow_mutating=False)` (the default) now
**blocks a `mutating` capability at pre-flight** via `InputValidator.check_mutating_consent` →
`safety_blocked:mutating_requires_consent`. Consent is threaded through the single shared boundary both entry
points funnel through (`src.cli.replay_capability`) via a `--i-understand-mutating` flag on BOTH
`python -m src.cli replay` and `scripts/run_capability.py`. Verified live: both entry points refuse without the
flag (exit 1, no mutation), both proceed with it. `read` capabilities are never affected.

**D3 fix — discovery-time safety enforcement (2026-08-25).** The gate previously ran only on the replay path;
the discovery agent never called `check_action`, so an LLM could in principle steer exploration off the allowed
surface. Fix: `DiscoveryAgent` accepts an injected `SafetyGate` and runs the **same `check_action`** in
`_handle_tool` before dispatch; an off-allowlist domain / unsanctioned action type is a **terminal**
`status="safety_blocked"` (not escalatable — mirroring replay). Wired enforcing in `src/cli.py::discover_capability`;
`None` (off) stays the default for tests/back-compat. Note: this uses the `src/safety` `SafetyViolationError`
(terminal block), distinct from the older `src/replay/results.SafetyViolationError` escalation seam.

**Consequences** — `hard_failure` now has a fifth reason string, `safety_blocked:<rule>` (distinct from the four
Phase-3 subtypes; decoded by `src/cli._explain_hard_failure`). Tests: `tests/safety/test_safety.py`
(allowlist/type/redactor + the D1 consent cases + evil-domain e2e) and `tests/agent/test_discovery_safety.py`
(D3 block/allow/back-compat). REPORT §6 documents the built layer; §7 notes the deferred items (config-driven
allowlist, screenshot redaction, broader redactor field-name coverage).

## Cuts   (明确标记"暂不做"的取舍)

### ADR-003 — Defer stretch goal: canonicalization / cross-tenant reuse demo
**Decision** — Do not implement the §8 stretch goal "Canonicalization / cross-tenant reuse" in this deliverable — no second-tenant-variant demo, no fork of ParaBank into an alternative variant. The schema-level foundation for this capability is already in place (parameterized locators + platform-agnostic descriptors, per ADR-002), but no runtime demonstration is included.

**Context** — §5 says "cut depth, not whole capabilities" — every core requirement (3.1–3.6) should be "thin but real" before polishing any stretch goal. §7 explicitly says "we do not reward feature breadth" and that "prematurely building scaling infrastructure is not [valuable]". Producing a cross-tenant demo would require building a second, slightly modified target variant (fork or mock), which is disproportionate to its evaluation payoff relative to strengthening the six core requirements.

**Alternatives**
- Actually build a second-tenant variant (fork/mock a ParaBank-like UI with minor differences) — would earn the stretch-goal points, but at engineering cost that competes directly with core-requirement quality. Rejected on payoff/effort grounds.
- Describe cross-tenant reuse in REPORT §4 without any code-level support — worst option: no demo, and no technical credibility either. Rejected.
- Chosen middle path: no runtime demo, but the architecture (parameterized locators, per ADR-002) genuinely supports cross-tenant reuse. The code itself is the evidence backing REPORT §4's design story.

**Consequences**
- REPORT §4 draws its technical credibility from the schema architecture (ADR-002), not from a runtime demonstration.
- REPORT §7 (Cuts) explicitly lists this omission and describes the concrete next step if resumed: create a URL-prefix variant of ParaBank, invoke the same artifact with a different `tenant_base_url` parameter value to demonstrate cross-tenant replay.
- This cut is reversible with no architectural rework: if time permits after the core six requirements are solid, adding the demo requires only producing a variant target — ADR-002's foundation absorbs the rest.
